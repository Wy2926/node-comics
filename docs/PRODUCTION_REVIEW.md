# 服务端生产就绪审查

日期：2026-09-16。审查基线：`d7f87ae`。结论：**暂不适合直接公开上线**。项目尚未上线，按全新数据库、全新部署审查；不要求旧数据迁移、旧 API 或旧调度兼容。

本轮为服务端 Review。按最终要求撤回全部自定义域名代码、配置与 Worker 文件，下载继续使用原有 R2 S3 签名。没有发布、部署、Git 提交、修改线上桶权限或调用付费模型。下述问题仍待修复／配置，不把“发现问题”记作“已修复”。

## 阻断公开上线的问题

### 1. P0：R2 公开域名可以绕过全部应用授权（真实验证）

`nodelane-comics-oss.nodelane.net` 当前直接绑定 R2 桶。本轮上传一张随机键的合成 PNG，通过该域名在**无 Authorization、无 Cookie、无签名参数**时取得 HTTP 200，响应字节与原图一致。仅创建并删除这一张测试图片，没有读取用户漫画。

后端的 `owned_asset()` 与 `access_json()`（[assets.py](../backend/app/assets.py)）只保护经 API 签发的链接；无法限制公开桶入口。持有对象路径的人能够绕过账户隔离、签名有效期和数据库删除状态。不可猜测的对象编号不构成访问控制。

上线前必须在 Cloudflare 关闭此桶的公开域名绑定，并检查 `r2.dev` 及其他公开绑定都已关闭。继续用 S3 预签名下载即可；不能仅从应用配置里删除域名。关闭后需再次验证公开访问被拒绝、授权 S3 下载正常。

脱敏探测结果：`artifacts/production-review/r2-public-domain-probe.json`，`anonymous_status=200`、`anonymous_bytes_match=true`、`cleanup=deleted_exact_probe_key`。

### 2. P1：本地启动配置仍允许免密码管理员登录，生产配置缺少启动校验

定位：[bootstrap.ps1](../scripts/bootstrap.ps1) 第 23 行、[main.py](../backend/app/main.py) 第 128–145 行、[auth.py](../backend/app/auth.py) 第 35–37 行、[config.py](../backend/app/config.py) 的 `validate_storage()`。

脚本生成 `DEV_AUTH=true`；本地 `deploy/.env.local` 实际也是此值。访问 `/v1/auth/dev` 只需提交用户名 `admin` 即可获得管理员令牌。API 绑定 loopback 能保护纯本地运行，但被反向代理公开后，该开发入口也会被公开。

根 `.env` 配置了部分 OIDC 字段，但两个环境文件合并后仍缺少 `OIDC_AUDIENCE`。直接改为 `DEV_AUTH=false` 会使受保护请求返回 `AUTH_UNCONFIGURED`，而启动与 `/health` 仍可成功。当前生产约束只强制 R2，没有完整校验 OIDC／PostgreSQL／生产来源；Compose 的 CORS 默认仍是 localhost。

应提供明确的生产启动配置与启动校验：禁止开发登录，要求 PostgreSQL、完整身份配置和精确生产来源。完成真实用户、管理员、普通用户无管理权限的 OIDC 验收。本地开发入口本身可保留用于隔离测试，但不能成为公开部署默认值。

### 3. P1：撤销 OIDC 签名公钥后，旧公钥仍可能长期有效（隔离复现）

定位：[auth.py](../backend/app/auth.py) 第 18 行：`PyJWKClient(..., cache_keys=True, lifespan=300)`。

项目安装的 PyJWT 2.14.0 将单个 signing key 存在没有时间过期的 LRU 中；`lifespan=300` 只控制 JWKS 集合缓存。缓存命中时不重新读取集合，因此身份服务删除某个 `kid` 后，已缓存它的进程仍会接受该密钥签发且尚未过期的令牌。若旧私钥泄露，攻击者还可以持续签发新的令牌，直到进程重启或该缓存项被淘汰。

复现使用本地生成的 ES384 密钥：首次取钥后清空可用公钥集合并使集合缓存失效，再取相同 `kid` 仍返回原对象并成功验证令牌，没有再次获取公钥集合。未访问真实身份账户。

应关闭无限期的单钥缓存，保留有 TTL 的 JWKS 集合缓存，补充公钥撤销／轮换／身份服务不可用的测试。已有 `test_oidc.py` 替换了整个 JWKS 客户端，因此没有覆盖此行为。

### 4. P1：在途容量与页数额度不能限制提交记录膨胀（隔离复现）

定位：旧 `submission_api.py` 第 103–199 行（现已删除，由 [plan_api.py](../backend/app/plan_api.py) 替代）、[jobs.py](../backend/app/jobs.py) 的 `create_job()`；请求中间件仅限制单次 body 大小。

每次使用新的 `Idempotency-Key`，都会创建新的 Submission／SubmissionItem。重复图片可以复用同一个活跃 Job，绕过新增任务容量和页数预占；重复使用同一幂等键的保护不能覆盖这种请求。

实际复现：普通账户先提交 1 页，再以三个不同幂等键各提交 500 个指向该页的条目。全部返回 202，每次新增页数为 0，最终仅 1 个 Job，却有 4 个 Submission、1501 个 SubmissionItem。每次还会在全局调度锁内执行整批处理与回执组装。仓库代码及部署模板中未发现对应的用户／IP 请求速率限制。

应对受理接口设置跨 API 副本生效的用户级速率／突发上限，并限制并发大请求；网关再提供 IP 级保护。明确提交回执保留策略，避免持续重复提交导致数据库增长。修复时保持合法多文件页复用和业务幂等，不以重复扣页数代替反滥用控制；PLUS 不限量常规翻译仍按既定产品规则执行。

## 其他代码风险与开发阶段取舍

### 5. P2：首次 OIDC 登录存在创建用户竞态

定位：[auth.py](../backend/app/auth.py) 第 44–53 行、[models.py](../backend/app/models.py) 的 `User.subject` 唯一约束。

两个首次请求可同时查询到用户不存在，然后分别 INSERT。第二个提交会产生 `IntegrityError`，生产 OIDC 分支未处理，最终成为 500；开发登录分支反而已有冲突恢复。阅读器首次登录并发加载多个 API 时可触发。隔离注入唯一约束冲突后确认异常从 `identity()` 直接逃逸；本轮未做该场景的真实 OIDC 并发请求。

应使用数据库原子 upsert 或唯一冲突后回查，并用 PostgreSQL 双会话覆盖首次登录。回查后仍按本次已验证 claims 同步角色。

### 6. P2：全队列扫描位于全局调度锁内，尚不能证明大规模生产吞吐

定位：[scheduler.py](../backend/app/scheduler.py) 第 174–210 行、[workers.py](../backend/app/workers.py) 的主循环。

`claim_stage()` 取得全局锁后，对所有符合阶段条件的待执行 JobStage／Job 调用 `.all()`，再在 Python 中筛选、分组和排序。控制进程每 250ms 尝试各阶段领取，所有副本共享此锁；提交、优先级和租约心跳也依赖它。

这是便于保证公平与一致性的首版实现，但队列规模没有全局上限，用户规模扩大时锁持有时间和内存随积压增长。现有并发正确性测试不能证明吞吐。应测量目标队列规模下的领取延迟、锁等待和心跳期限，并采用保持用户公平的数据库候选集查询。不能简单对全队列加固定 LIMIT，以免后排用户饿死。

### 7. P2：健康与故障可观测性主要停留在开发运行层面

定位：[main.py](../backend/app/main.py) 第 112–115 行、[workers.py](../backend/app/workers.py) 的 `main()`／`_heartbeat()`、[dispatcher.py](../backend/app/dispatcher.py) 的 `main()`、[compose.yaml](../compose.yaml)。

`/health` 仅执行 `SELECT 1`，不能说明 OIDC 可用、控制任务在消费或维护进程在回收过期租约。Worker 丢弃完成的 Future 时不读取异常；心跳失败直接退出线程；维护循环对全部异常只打印同一条通用警告。Compose 为数据库和引擎提供 healthcheck，但未给 API／控制执行／维护进程提供等价就绪监控。

应区分存活与就绪状态，记录不含密钥、签名 URL 或图片全文的错误类别／任务 ID／阶段指标，对控制池失联、队列长期无进展、未知调用和维护失败告警。进程自动重启与租约恢复已有实现，缺的是可诊断与可告警的生产闭环。

### 8. 运维验收缺口：备份恢复、入口配置与实际容量

- PostgreSQL 目前是 Compose 持久卷，仓库未提供可验收的备份、恢复演练及数据库/R2 一致恢复流程。孤儿扫描会删除超过一天且在当前 DB 无引用的对象（旧 `storage_cleanup.py` 第 41–65 行，现已删除）；恢复较早数据库后，在核对对象引用之前不得启动清理。全新部署也需要未来灾难恢复方案，这不涉及旧数据迁移。
- 正式 HTTPS 反代、生产 API CORS、R2 下载 CORS 和真实 OIDC 登录仍需在目标部署验收；本轮没有操作线上反代／身份平台设置。
- 上传经 API 缓冲后写 R2，计算节点经 API 获取原图，渲染结果使用 JSON/base64 回传。这是当前明确实现，不能等同于图片流量全部绕过控制服务。多并发大图的 API 内存、带宽和连接池需要容量测试。
- 本轮没有执行新版本真实 GPU 推理、付费图片模型效果验收、跨物理机故障注入、依赖漏洞扫描或正式压力测试。已有其他任务的历史证据可以参考，但不能替代本次生产环境验收。
