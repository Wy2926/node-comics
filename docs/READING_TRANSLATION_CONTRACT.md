日期：2026-09-20。状态：**新环境代码已实现并完成隔离验证；未替换现有服务或部署**。本文保留设计依据，最终接口以 `contracts/openapi.json` 与当前源码为准。最终数据库基线为 `payments_0001`，只接受全新空库。完成结果复用不创建任务，只保留私有授权和回执，见[译图共享与匹配](RESULT_SHARING.md)。

用户已明确使用新库、新环境开发：实现时直接删除被替代的数据库结构、迁移链、旧接口与旧客户端逻辑，以最终模型重建初始数据库基线。不做旧数据迁移、历史接口适配、双写或兼容回退。下文提到当前实现只用于说明改造位置，新契约的刷新/断网幂等恢复仅针对新环境自己产生的任务。

目标是让当前页尽早开始翻译、后两页提前准备，客户端只表达阅读需求，服务端负责准入与调度。正常阅读不查询队列，不等待服务端下发防抖参数。用户继续看到原图及图内状态，译图下载、解码完成后原位替换。

## 2. 阅读触发与客户端职责

阅读器每本漫画默认查看原图，不创建新的翻译阅读需求。手动选择常规／AI 或显式打开译本后才应用下面的触发规则；查看方式在本机按作品隔离并保留，原图模式向协调器提供空需求窗口。已受理任务的恢复与完成不受影响。

以下时间是首轮调优建议，需浏览器实测，不是已实现值或用户时延承诺。

| 行为 | 初始建议 |
| --- | --- |
| 首次打开、点击翻页、目录跳转、手动翻译 | 原图描述符就绪后立即申请当前页，0ms 人为防抖 |
| 连续滚动产生新的当前页 | 本地合并 80ms；持续滚动最多每 200ms 发出一次最新窗口，不无限延后 |
| 后两页预取 | 当前页身份稳定约 150ms 后补齐；原图准备与当前页请求并行 |
| 同页微滚、布局测量、任务快照更新 | 不重置计时、不递增窗口序号、不重发计划 |
| 分钟限频到期或权益升级且存在待受理页 | 立即重新评估最新窗口，不再附加 450ms 防抖；任务完成只更新图片，不补回分钟名额 |
| 正常阅读会话续期 | 可见且活跃时约 30 秒一次，服务端租期保持约 90 秒；不附带新生成操作 |

“提高请求频率”体现为有新需求时迅速申请。窗口没有变化、已受理页仍在运行时，不循环提交同一张图。一次最多当前页与后两页；三页是预测阅读范围，不是账户并发上限。只要分钟额度允许，可以继续受理新窗口，已有任务未完成也不阻止提交。

客户端协调器维护四类本地状态：最新阅读窗口、已冻结但回执未知的操作、已受理任务/上传、各类阻塞条件。每个会话最多一个计划请求在途；其间发生多次变化只留下最新窗口。旧响应里的已受理任务必须落盘，但不能把 UI 或优先级切回旧窗口。

能力和权益在登录/打开时加载并缓存，配置或权益变化时刷新；提交仍由服务端校验。热路径不再由 `available_slots`、硬编码 3/10 或本地权益快照决定服务端能否受理；本地可展示明确的权益错误，但不能因此跳过免费结果复用。

上传/下载使用已有有界并发，控制请求和长轮询不占图片传输名额。当前页优先获得上传、下载与解码机会，后两页准备失败不阻塞当前页。大图哈希和后页采集也不能成为当前页控制请求的串行前置步骤。

## 3. 阅读计划接口

统一为 `POST /v1/translation-plans`，用 `trigger=reading` 表达自动阅读，`trigger=manual` 表达显式重试/重译。两者共用新的逐页受理、分钟计数、额度、复用与结算逻辑。删除 `POST/GET /v1/translation-submissions` 及其旧整批原子契约；不为旧客户端或旧回执保留入口。

请求的概念结构如下。`image` 沿用现有图片描述符及校验规则，示例为结构说明，非完整可执行请求：

```json
{
  "trigger": "reading",
  "session_id": "reader-session-uuid",
  "sequence": 42,
  "priority_epochs": {"classic": 7},
  "items": [
    {
      "page_key": "local-page-20",
      "operation_key": "persisted-operation-uuid",
      "role": "current",
      "mode": "classic",
      "target_language": "zh-Hans",
      "max_quota_pages": 1,
      "image": {"client_item_id": "local-page-20", "image_sha256": "<sha256>", "byte_size": 1000000, "content_type": "image/jpeg"}
    }
  ]
}
```

- 最多三项，最多一项 `current`，其余按数组顺序为 `prefetch`。当前页尚未就绪时不申请其后页的新任务；允许空列表表达退出自动窗口。每项模式独立，分钟计数按账户跨模式、语言、设备合并。
- 本地原图未就绪时先准备已知当前页，后两页就绪后以新的 sequence 更新完整窗口。描述符只含摘要、必要格式/大小与可选本人资产或文件页标识，不发送源站 Cookie、登录令牌或签名图片地址。
- 已知任务可携带本人 `job_id` 绑定窗口；这是引用校验，不能修改 operation 对应的生成内容。`trigger=reading` 只允许默认的 `action=ensure`。`trigger=manual` 每次一项，允许 `action=retry/regenerate`，提供本人来源 Job 与必要的未知成本确认；无阅读会话时按普通优先级受理。会话/序号规则只对携带阅读窗口的请求生效。显式新生成使用新 operation key，不能通过自动滚动构造。
- `page_key` 用于本会话页面关联，不是授权凭据或跨用户复用依据。`operation_key` 在发送前持久化，作用域为账户；绑定不可变图片身份、模式、语言、业务额度上限及显式生成选项，不绑定位置、role、session 或 sequence。
- 生成操作一旦受理，回执永久指向原 Job 与实际配置版本。默认模型或有效配置发生变化，不得让同 key 再生成一遍。用户显式重译才建立新的操作键；删除访问记录或操作回执归档，也不能把旧键变成新任务。
- 同 session 的 sequence 单调增加；同 sequence 必须是相同窗口摘要。可以重发同一计划并重新评估未受理项，但不能用相同 sequence 改动窗口。旧 sequence 可以返回已存在回执，不能准入旧窗口中的新任务或恢复旧优先级。

服务端在短事务中按当前页、后第一页、后第二页处理：查操作回执 → 查本人已有任务/有效结果及全局完成结果复用 → 校验新任务权益与滚动分钟额度 → 必要时原子记录分钟消耗、Job、上传会话和页数权益预占 → 绑定阅读优先级。网络、R2 和模型调用均在事务及锁外。

请求体/身份/控制请求反滥用等整请求检查在逐项受理前完成。逐项用 SAVEPOINT，或等价的拒绝前零写入机制：页级拒绝必须回滚该项 Job、资产授权、分钟消耗、页数预占、上传会话与回执，保留其他成功项；内部异常则整个事务回滚。一次响应只在事务提交后发出，数据库事件也只在提交后通知。因此不会出现接受了第一页却因第二页限频而返回无回执的整请求错误。

每项返回以下 disposition：

| disposition | 含义 | 客户端动作 |
| --- | --- | --- |
| `ready` | 已有可用译图或无字结果，含授权访问记录 | 优先下载/解码；无字页保留原图 |
| `pending` | 同一操作或可复用的本人任务已在途 | 绑定 Job；恢复必要上传并等待变更，不再创建操作 |
| `accepted` | 本次新建持久翻译任务，已经消耗一次分钟名额并预占必要页数权益 | 保存回执，按上传计划继续，等待完成 |
| `deferred` | 尚未受理，`IMAGE_RATE_LIMITED` 表示本滚动窗口的新图片额度已满 | 保留最新窗口中的该页；按返回的时间等待，不查队列 |
| `blocked` | 权益、图片、已失败/取消任务或未知结果需要处理 | 按业务码显示升级、重新采集或手动恢复；不自动换键重提 |

混合响应示例：

```json
{
  "session_id": "reader-session-uuid",
  "applied_sequence": 42,
  "priority": {"classic": {"owned": true, "epoch": 7}},
  "policy_revision": "12",
  "image_rate_limit": {"window_seconds": 60, "limit": 30, "remaining": 0, "retry_after_seconds": 8},
  "items": [
    {"page_key": "p20", "operation_key": "op20", "disposition": "accepted", "job": {"id": "j20", "status": "awaiting_upload"}, "upload": "<沿用现有 UploadPlan>"},
    {"page_key": "p21", "operation_key": "op21", "disposition": "ready", "job": {"id": "j21", "status": "succeeded", "output_asset_id": "a21"}},
    {"page_key": "p22", "operation_key": "op22", "disposition": "deferred", "code": "IMAGE_RATE_LIMITED", "retry_after_seconds": 8}
  ]
}
```

示例只列关键字段，实际 Job、上传授权与资产访问沿用现有安全契约。`deferred` 没有新 Job、上传会话、分钟消耗或页数预占，服务端也不承诺自动执行它。服务器只保存有界的最新窗口元数据；待受理工作由可见客户端保留。已受理任务则可以持续在后台排队，不再设账户 3/10 上限。

## 4. HTTP 状态和重试

使用标准 HTTP 状态加稳定业务码，不发明私有状态码。逐页结果始终是判断该页是否已受理的依据。

| HTTP | 适用情况 | 行为 |
| --- | --- | --- |
| `202` | 本次至少有一页 `accepted` | 逐页保存回执；不代表其他页也被受理或翻译已经完成 |
| `200` | 没有新建任务：已有结果/任务、窗口更新、或混合逐项拒绝结果 | 逐页处理；可能含 `deferred` 与 `blocked`，不能全部当成功或全部重试 |
| `409 STALE_READING_PLAN / READING_SEQUENCE_CONFLICT` | 窗口过时或同序号不同内容 | 不准入新任务；以最新窗口继续，未知旧操作另行核实 |
| `429 IMAGE_RATE_LIMITED` | 没有 ready/pending/accepted，且所有非空项均因分钟额度 deferred | 返回完整逐项结果与 `Retry-After`；等待后只重试最新窗口 |
| `429` 其他 code | 控制请求速率、请求处理并发或等待连接达到限制 | `Retry-After` + 机器码 + 重试作用域；与每分钟新图片数量分别处理 |
| `503` | 服务过载或暂不可用 | 已知未受理时按 `Retry-After`；提交结果不确定时先核实原键 |
| `401 / 403` | 未登录或整请求无访问权限 | 恢复身份或处理权限；单页额度不足通常用该项 `blocked` 返回 |
| `422` | 整请求结构或窗口长度非法 | 不自动重试；合法请求中的页级业务问题逐项返回 |

`202` 表示已接受处理但尚未完成，`409` 表达当前资源状态冲突；两者不能替代任务回执。[HTTP 语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)

`429` 表达速率限制，可附 `Retry-After`。[RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) 错误包保留 `error.code`、`error.retry_after_seconds`，增加 `error.scope`（新翻译图片/控制请求/等待连接），CORS 暴露 `Retry-After`。混合 200/202 的分钟等待放在逐项结果及 `image_rate_limit` 中，不能阻止已受理页继续上传。单项 `IDEMPOTENCY_CONFLICT` 用 `blocked` 返回并回滚该项，不能静默换键，不能让其他已受理项丢失回执。不把成功响应变成客户端防抖参数。

具体重试规则：

1. 图片限频：账户范围保存服务端返回的最早重试时间，同一待受理项到期前不重提；任务完成不清除它。普通升级 PLUS 或策略变化时，根据新的 policy revision 重新判定。客户端不按 remaining 自行分配额度，服务端仍原子准入。
2. 其他速率限制：控制请求被限流后，翻页和任务事件不能绕过对应截止时间；保留最新窗口，到期后合并发送一次。连接限流只影响连接，不无条件冻结上传或任务提交。图片限频期间已受理上传照常继续；新窗口如需查免费结果，可发送 `allow_new=false` 的同一计划，服务端只匹配和更新阅读意图，不创建新的计算任务、不计分钟消耗，但允许建立本人的结果授权。未命中项为 `deferred/NEW_TRANSLATION_NOT_REQUESTED`，不能据此返回分钟限频 429；控制请求预算仍生效。`allow_new` 不属于窗口内容摘要。
3. 网络错误：使用带随机偏移的 1、2、4、8 秒退避，最大约 30 秒，离线时暂停；未收到确定拒绝就保留原 operation key。恢复原有重绘 Job 不等于再次请求图片供应商。
4. 权益不足：等待策略/权益版本变化、额度恢复时间或用户操作；不每秒请求。图片无效、访问撤销、失败、取消和结果未知分别处理，不归入分钟名额重试。

图片准入与控制请求反滥用分开：普通 30／PLUS 100 是已确认的新图片分钟额度，不是 HTTP 请求数。当前控制请求保护默认账户 300 次/分钟、burst 30，每会话最多一个计划请求在途；它是独立于图片数的 HTTP 保护，目标部署可按实际负载调整。所有生成路径统一进入新计划接口和图片分钟账本；匹配/回执/租约/等待接口另设适当保护，增加副本不能获得额外图片额度。

同时移除旧批量提交专用的 500 页入口、大批次并发规则，以及按每天新增提交清单数/描述符数阻断正常翻译的规则。新任务受明确的分钟速率和既有套餐页数权益约束，回执增长通过受理速率、拒绝不落持久回执、精简逐页回执控制，不另设隐含的 PLUS 每日生成数量上限。

## 5. 滚动 60 秒图片计数

| 事件 | 是否消耗一分钟内的一张 |
| --- | --- |
| 新图片第一次受理并创建真正需要计算的 Job | 是 |
| 已有原图，新增模式、语言、配置版本翻译或显式重译 | 是 |
| 原键重放、PUT 重传、上传确认重发、已有本人在途任务复用 | 否 |
| 直接复用有效完成结果，只建立本人的结果授权与操作回执，不创建 Job | 否 |
| 受理前校验失败，或新任务事务/SAVEPOINT 回滚 | 否 |
| 已受理后取消、上传超时、图片校验失败或计算失败 | 不返还已消耗的分钟名额；页数权益按原有结算/释放规则独立处理 |

这限制的是**新增翻译图片的受理速率**，不以实际开始传输或传输成功的秒数计量。避免先建立大量 Job，等到 PUT 图片才发现已超过分钟限制；上传失败重传也不会被重复计量。

- 采用精确滚动窗口 `(server_now - 60s, server_now]`，不用自然分钟重置，也不用允许超出滚动上限的突发令牌桶。允许一口气受理剩余名额，不强制普通每 2 秒一张或 PLUS 每 600ms 一张。
- 在共享的新 Job 准入函数内，以既定 scheduler → user 锁顺序锁定账户，在锁内判定操作回执/本人在途任务/完成结果复用，再统计分钟事件并创建新计算 Job。锁外查询只能作提示，必须锁内复核，防止两个设备同时查无结果后重复准入。使用取锁后的数据库时间；分钟事件与 Job、回执、页数预占同事务提交。
- 事件以真正的新计算 Job ID 唯一，按 `(owner_id, admitted_at)` 建索引。HTTP 请求、图片上传会话和结果授权均不能重复插入事件。并行设备、更换 operation key、切换 reading/manual，都不能突破同账户 30/100；旧提交路由应已删除并返回 404，而非兼容转发。
- 事件短期保留并定期清理；清理过期事件不删除 Job 或永久幂等墓碑。计数不依赖 Job 当前是否仍运行，不在任务结束时扣减。
- 当前有 `count >= limit` 个未到期事件时，下一张的等待时间取按时间排序第 `count - limit + 1` 个事件到期，再向上取整秒返回 `Retry-After`。普通刚满 10 时通常等待最老一项到期；PLUS 降级后窗口内可能有 100 项，不能仅等最老一项。每次只承诺可重试时间，其他设备可能先消耗恢复名额。
- 服务端同时返回 `server_time`、`retry_after_seconds` 与 policy revision；客户端以单调时钟计算截止时间并加少量随机延迟，不依赖设备时钟准确。响应到来较迟时可保守多等一个网络往返，不提前突破限制。
- 普通每日 30 页、PLUS 重绘周期额度等保持现有独立约束。每分钟可以申请 10 张，不代表普通每天的额度增加；免费完成结果继续按既有规则复用。

删除账户 `QUEUE_FULL`、3/10 计数拒绝、下一上传空位预留及由套餐实时名额阻止受理的逻辑。节点计算线程、供应商并发、上传连接和字节限制属于实际资源保护，仍需保留；不能借这些字段恢复另一套账户待处理数量上限。取消在途上限后积压可能增长，通过实时阅读优先、公平执行、全局过载返回 503 和资源监控应对，不承诺所有已受理图片同时计算。

## 6. 增量同步与定时恢复

扩展已有 `GET /v1/me/translation-changes`，保留 `cursor`、`items`、删除标记、`has_more` 和 `wait_seconds=20`；增加客户端已知的 `policy_revision` 请求参数与服务端当前值，覆盖权益及分钟规则变化。没有变化时正常持有连接，变化时立即返回；20 秒空响应后才重连，约每分钟三次空等待请求，不是每秒查队列。

- 直接把返回增量、删除标记和游标在本地同一事务应用。`has_more` 才继续分页；不丢弃 payload 再从相同游标请求一遍。计划响应可以更新 Job 缓存，但不能用其回执跳过账户 feed 中尚未消费的游标区间。
- Job 游标表示任务可见状态变化，policy revision 表示权益/分钟规则变化，两者独立。OCR 进度、任务状态变化、上传完成、租约续期和普通分钟消耗本身不增加 policy revision，也不提前唤醒图片限频重试。
- 升降级、赠送、额度周期恢复、后台修改分钟上限，以及失败/取消/超时结算使可用页数权益增加时，策略状态与版本一致读，事务提交后唤醒。即使 `items=[]`，版本变化也立即返回；自然到期必须通过维护或快照对账正确反映。客户端按阻塞原因重新协调：页数权益释放可以唤醒额度不足项，但不返还分钟消耗，也不能仅凭通用 revision 变化绕过图片限频截止时间；只有实际分钟策略改变才提前重算该截止时间。
- 正常分钟名额恢复用拒绝响应给出的截止时间调度，不为每个 60 秒事件新增持久定时任务或分钟轮询。定时到期只协调一次最新窗口，再由服务端原子判断；暂停、隐藏或离线期间不补交历史预取窗口。
- **乱序防护**：feed 的策略增量包含当前套餐、分钟上限和权益摘要。若升级后的策略版本 13 先到，随后才收到标注旧版本 12 的图片限频响应，应比较实际分钟策略，确认上限变化后忽略旧策略阻塞并协调一次；仅页数权益释放不能跳过分钟截止时间。不同作用域的控制请求限流仍须遵守。Job feed 游标和策略版本单调合并。
- 继续复用数据库持久状态与提交后 `LISTEN/NOTIFY`。通知只负责唤醒，断线恢复从持久游标补齐；服务端已有约 5 秒对账可作为漏通知兜底，不把这个间隔转为客户端短轮询。
- 可见阅读界面维持订阅；隐藏/关闭后停止未受理预取及续租，已受理任务由服务器继续执行。原网页通过活跃 content script 驱动有界后台请求；令牌留在可信扩展上下文，不交给网站，也不依赖 MV3 worker 永久存活。
- 第一版每个活跃阅读上下文最多一条订阅，沿用账户连接上限并补齐 `WAIT_BUSY` 的 Retry-After。多标签可共享订阅，但不是正确性前提；刷新、重开、worker 重启必须按持久游标恢复。断连重连退避，不能另开 4 秒状态轮询补漏。

## 7. 优先级、多设备与过时请求

阅读计划保存跨模式的最多三页窗口；沿用每模式已有的会话控制权，在服务端执行跨模式分钟速率约束。无需客户端读取或填写 queue `expected_version`，不再下发套餐 3/10 实时名额作为阅读准入限制。

拥有对应模式优先级租约的会话在新任务准入时同时写入 `priority_rank` 与实时资格，消除“先变成普通队列任务、稍后再提优先级”的间隙。当前页优于本窗口两张预取，离开窗口的旧任务降为后台优先级；会员权重、跨用户公平和运行中任务非抢占规则继续生效。

每个模式的优先级租约增加服务端 epoch：

- 首次进入在没有有效控制者时取得租约；返回 epoch，后续计划携带它。
- 同 session 只比较本 session sequence；不同设备的 sequence 不能互相比较。
- 另一设备仍有有效租约时，不让后台周期请求自动接管。明确的前台接管动作携带已知 epoch 做条件更新，只允许一次成功；旧请求不能用更大的 sequence 抢回租约。
- 有效但未取得优先级控制权的会话仍可复用或正常受理任务，但返回 `priority.owned=false`，只按普通优先级执行，不修改另一会话的顺序。被接管/过期并已失效的 session epoch 则不能准入新任务，只能核实已有操作；明确区分会话有效性和优先级所有权。退出/过期只撤销自己的优先级，不取消已受理任务。
- 会话续租使用独立的 `PUT /v1/reading-sessions/{session_id}/lease`，只处理租约与条件接管，不重新准入 deferred 页。客户端在窗口/优先级状态没变化时不制造新的任务 change 事件。

sequence 与窗口摘要必须在任何新任务准入前校验；窗口更新与该次准入在相同锁顺序下提交。若旧计划已经先完成受理，则保留其任务，随后新窗口只修改其阅读优先级。不再设置 `reserve_next_upload`，也不等待任务完成腾出账户空位。

首版不自动取消已受理任务，包括旧窗口的后两页；未受理的旧窗口可以直接替换。未来如回收尚未执行的过时预取，需另加原子取消/页数权益释放、共享引用及租约竞态验证，且不返还分钟消耗。取消用户在途上限后，新当前页可在分钟额度内立即受理，但仍可能等待正在运行的非抢占计算；更快受理不能被描述为模型推理加速。

## 8. 幂等恢复与存储边界

计划是可更新的阅读意图，操作回执是不可重新执行的生成事实。两者不能使用同一个整体幂等键冻结，否则首次返回 deferred 后永远只能回放旧拒绝。

- 为每项保存 operation → request hash → Job/上传/实际配置的映射；同内容自动请求仍可通过既有去重映射到同一 Job，不重复计算分钟消耗或页数权益。相同操作回放不新增回执，拒绝计划不无限创建持久失败回执；已受理操作的精简幂等回执永久保留。
- 最新窗口元数据只保存有界会话和至多三项，租约过期后不自动受理，也不产生额度。活动会话数量要有账户上限；历史窗口不作为新队列累计保存。失效 session/epoch 的晚到请求只能核实回执，不能恢复控制权或创建旧页。
- 新增只读语义的 `POST /v1/translation-operations/resolve`，一次最多查询十个本人 operation key，返回已受理、未找到或回执已归档/访问已撤销。用于新环境内响应丢失、刷新或上一阅读窗口已被替换后的恢复；不创建任务、不扣额度、不调用供应商，不探测 R2。插件已移除独立翻译记录页及其分页查询和轮询；服务端 `GET /v1/translation-operations` 保留，阅读器继续通过 resolve 和账户增量接口恢复状态。
- `not_found` 只表示本次快照尚未见到回执，不证明原请求永不会提交。原请求与恢复受同一键及锁约束：仍属最新窗口时可以用原键重试；已离开窗口则只核实，不补发旧生成请求。原请求最终受理的信息从响应、核实接口或账户 feed 合并。
- 成功回执和上传状态先落 IndexedDB，再继续有限并发上传；中断后重取有效授权，不能因为新窗口生成了新序号就抛弃旧任务。已受理但尚未上传的占位按既有 TTL 处理。
- 账户切换以 API origin + user ID 隔离本地游标、操作、图片与结果。feed、resolve、job 引用及所有下载继续验证所有权；旧响应不能写入新账户。

实现可提取当前 `JobRequest` 中仍有价值的幂等算法，数据模型按新契约直接收缩为逐页操作回执、窗口/会话、分钟事件与现有必要的任务/资产/结算模型。删除仅服务旧 Submission/SubmissionItem、容量、预留位及旧接口的结构与字段，不同时维护两套操作账本；重建最终 schema 的初始迁移，不编写旧库升级或回填分支。
