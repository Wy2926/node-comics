# 图像引擎 CPU/GPU 流水线

2026-09-17：`services/classic-engine` 将整阶段设备锁收缩到模型调用，保持一个模型实例。此改动不改变权重、FP32 精度、分辨率、OCR／掩膜／嵌字算法和缓存身份，沿用原引擎版本；执行架构通过 `/health.pipeline.implementation = cpu-device-overlap-v1` 标识。没有自动修改已有节点执行位、重启业务节点或公开部署。

## 执行边界

| 通道 | 容量及职责 | 物理设备锁 |
| --- | --- | --- |
| 入场 | 同时最多 3 个阶段；取得名额后才读取请求体、解码图片 | 不持有 |
| CPU | 一个工作线程，执行解码、哈希、区域合并、掩膜细化、裁剪规划／复制／回贴、最终编码 | 不持有 |
| 设备 | 一个专用线程，检测＋OCR；CUDA/CPU 每次 LaMa 裁剪调用 | 调用期间持有 |
| Qt 排版 | 一个 spawn 子进程，Qt 初始化和排版均在其主线程；图片经进程通信传递 | 不持有 |
| 分格 | 沿用一个 CPU 子进程，每个已入场 analyze 至多一个工作项 | 不持有 |

例如 A 页做排版时，B 页可以推理；A 页掩膜细化时，已经完成解码的 B 页可以推理。CPU 通道自身串行，因此不能承诺解码、掩膜和 PNG 编码彼此同时执行。模型调用内部的 CPU 预处理仍随该调用持锁，本轮没有拆改上游网络内部实现。

DirectML 沿用两个私有 LaMa 子进程。该池包含 CPU FourierUnit、数据搬运和裁剪调度，仍在一个设备锁区间内完整运行／排空；不能与检测／OCR 同时使用设备。CPU 后处理与排版可以在池执行期间重叠。CPU 模式复用同样通道，但可能争用 CPU 资源，不能推断具有相同加速比。

物理锁继续使用同一 `resource_id` 对应的共享文件，不伪造节点身份、不增加模型副本。锁只协调遵守该协议的引擎。服务端默认一个节点执行位保持不变；启用新代码后，配置至少 2 个执行位才有跨请求重叠机会。3 是引擎内部在途上限，不是建议把每台设备设置为 3；更高的代理执行位会增加等候请求，需结合实时页延迟和吞吐判断。

## 生命周期与隔离

- 缓存元数据只由服务事件循环访问；工作线程拿到当前请求持有的数组引用。缓存淘汰不会撤销正在使用的数组，scope/hash/config/checkpoint 绑定与原图缓存失效 410 协议保持不变。render 缺缓存时先经过设备通道恢复抹字，再送排版。
- HTTP 协程取消后，已提交的本地线程／子进程工作必须结束才归还设备锁和入场名额；重复取消同样等待。CUDA 在正常完成或异常路径上同步设备，避免未完成 kernel 越过锁的释放边界。分格与 DirectML 子任务也要排空。
- Qt 进程崩溃令当前阶段失败；下一次排版请求重建子进程并应用上次成功配置，不在失败页内偷偷重做整阶段。原有控制端租约和重试规则不变。
- 热更新准备资源后阻止新入场，等待已有 CPU、设备、排版和编码结束，再更新各执行通道的配置与缓存。应用失败回滚，回滚失败取消 ready，不继续接单。
- 上游 stdout/stderr 在工作线程中按线程抑制，排版进程独立抑制；不在并发线程里使用全局 `redirect_stdout`。报告只含时序、配置与哈希，无对白。

## 观测与复现

健康信息新增流水线实现、入场容量、当前活跃数和通道数；`inference_serialized=true` 继续表示模型调用串行。阶段 `timings` 增加带 `analyze_`／`inpaint_`／`render_` 前缀的指标，避免控制端合并阶段计时时覆盖：

- `admission_wait`：等待引擎在途名额／配置排空的时间。
- `device_wait`、`device_hold`：累计等设备锁、持设备锁时间；后者包含模型内部 CPU 工作及设备同步，不是纯 GPU kernel 时间。
- `cpu_wall`：CPU 通道提交到完成的累计墙钟时间，包含该通道排队。
- `layout_wall`：排版通道提交到完成的墙钟时间，包含排队、进程传输和必要恢复。
- `request_wall`：服务入口到阶段结果完成，包含入场等待；不包含客户端到服务器网络和最终 HTTP 发送。

保留 `detect_ocr`、`inpaint`、`render` 等原指标。它们与上述细分指标存在包含关系，不能全部相加；并发页的累计耗时也不能当作整池墙钟耗时。

使用已有 CUDA 或 CPU 原生环境、已校验模型与字体，在仓库根目录执行，输出目录必须不存在：

```powershell
services/classic-engine/.venv/Scripts/python.exe scripts/benchmark_pipeline.py --directory private-test-data/pipeline-repeat --pages 12
$env:PYTHONPATH = "$((Get-Location).Path)/engines/mit-native"
services/classic-engine/.venv/Scripts/python.exe -m pytest services/classic-engine -q
```

基准默认 `portable-v1`、CUDA、PyTorch 4 线程／OpenCV 2 线程，依次测 1／2／3／1 个客户端，每组相同总页数。每页使用独立 scope，同页正常复用原图和抹字缓存。预热和顺序执行参考不计入吞吐；逐页核对分析、抹字像素、布局、最终像素及恢复标记。默认空白页只作质量／空结果检查，`--include-blank` 才将其计入吞吐；可重复传 `--image` 添加样本，`--device cpu --neural eager` 检查 CPU 路径。

该脚本使用进程内 HTTPX ASGI transport，保留请求校验、编解码、真实模型和进程通信，不覆盖真实 TCP、LLM、R2 或集群公平调度；无需付费调用。私有报告／图片留在指定目录。没有引入新依赖、模型、字体或第三方源码。

## 本地验证

Windows、i9-13980HX、RTX 4060 Laptop 8 GiB、PyTorch 2.5.1+cu124；`portable-v1`，PyTorch 4 线程／OpenCV 2 线程。1024×1536 原创漫画，固定短中文译文，每组 12 页，空白页不计入下表。**比较的是新流水线的不同请求并发数，不是改动前后的发布版本跑分。**

| 同时在途页面 | 吞吐（页/分钟） | 平均单页 | P95 单页 |
| --- | --- | --- | --- |
| 1 | 23.92 | 2.50 s | 2.56 s |
| 2 | 29.77 | 3.97 s | 4.34 s |
| 3 | 31.66 | 5.50 s | 6.46 s |
| 1，收尾复测 | 22.37 | 2.68 s | 2.82 s |

两路比前后单路吞吐约高 24–33%，三路比两路只再高约 6.3%，延迟继续增加。各组 PyTorch 活跃显存峰值一致（1,298,850,816 bytes，约 1.21 GiB），保留池峰值一致（2,095,054,848 bytes，约 1.95 GiB）；这不含桌面和其他进程显存，不能等同于整卡占用。没有加载第二个模型副本。建议此设备先用两个执行位，再根据实际页面及实时延迟调整。

48 个计时页均与顺序参考的分析、抹字、布局及最终像素一致，无缓存重建；另已核对空白页。首轮漫画／空白各半的 48 页测试同样一致，但其吞吐不与全漫画表混用。CPU/eager 路径另测 1／2 路共 4 个漫画页，输出一致，仅作为功能验收，不作为 CPU 容量建议。已查看最终图，固定短译文用于检查执行等价性，不是翻译质量验收。

自动化测试覆盖设备调用互斥、CPU 后处理／排版与推理重叠、Qt 子进程主线程、重复取消后排空、异常同步、排版进程崩溃恢复、配置排空／回滚、缓存跨任务隔离及失效恢复。GPU 实测没有覆盖 Windows DirectML；其池内调度保持原有方式。未构建 Linux 容器或重启生产节点。
