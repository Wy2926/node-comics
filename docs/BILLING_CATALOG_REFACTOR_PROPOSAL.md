# 可配置商品、Paddle 支付与权益发放重构方案

日期：2026-09-17。状态：**方案待评审，尚未实现**。

本次用户要求：调研成熟开源方案；后台按 Paddle ID 绑定 PLUS、额度等权益；动态展示可购买商品；重构支付，不兼容旧表、旧数据和旧代码，删除后续无用实现。本文件只确定方案，不修改支付代码、不操作支付账户、不删除数据库。

用户本次要求已扩展此前“唯一 PLUS 套餐、不出售额外页数包”的产品边界。新设计支持配置这些商品，但示例商品不表示已经定价、上架或开始收费。现有实现事实仍参考 [Paddle 接入记录](PADDLE_BILLING_DESIGN.md) 和 [会员额度设计](MEMBERSHIP_AND_QUOTAS.md)。

## 1. 推荐方案与开源调研

推荐：**Paddle 官方开源 Python SDK + 项目内独立的商品目录、版本化权益规则和发放服务**。继续使用 FastAPI、SQLAlchemy、PostgreSQL 和现有 React 管理后台，不增加 PHP/Ruby 支付服务。翻译端只读取有效权益与额度，不读取 Paddle 产品或价格 ID。

这不是宣称 SDK 已包含完整的无代码权益后台：SDK 负责 Paddle 协议，商品和权益配置是本项目需要实现的业务层。调研范围内没有验证到同时满足“成熟、原生 Paddle Billing、自托管、可直接嵌入现有 Python 工程、后台配置本项目权益”的成品。

| 方案 | 已核实能力与维护证据 | 对本项目的判断 |
| --- | --- | --- |
| [Laravel Cashier Paddle](https://github.com/laravel/cashier-paddle) | Laravel 官方组件，MIT；2.x 支持 Paddle Billing、订阅、试用、取消、单次收费及 Webhook；调研时发行页最新 v2.8.1 | 成熟的 Paddle 集成候选，但要引入 Laravel/PHP；仍需开发权益绑定、额度账本和商品后台，不作为本项目直接依赖 |
| [Rails Pay](https://github.com/pay-rails/pay) | MIT；包含 Paddle Billing 适配，统一客户、订阅、支付记录及异步回调处理；调研时发行页最新 v11.7.0 | 可参考职责拆分，但要引入 Rails/Ruby，不能直接解决现有额度的原子预占与释放 |
| [Lago](https://github.com/getlago/lago) | 开源计量与账单平台，仓库主许可证 AGPL-3.0；官方原生支付列表没有 Paddle，文档将其列在自定义支付集成场景 | 要另外开发 Paddle 适配，还会增加独立的账单/订阅系统；与 Paddle 已承担的职责重叠，不推荐 |
| [Paddle Python SDK](https://github.com/PaddleHQ/paddle-python-sdk) | Paddle 官方维护，Apache-2.0；支持 Billing API 和验签；要求 Python 3.11+；调研时最新 v1.15.0 | 推荐作为协议依赖，与当前后端语言匹配；不把 SDK 当作权益管理成品 |

来源：[Cashier 当前文档](https://laravel.com/docs/13.x/cashier-paddle)、[Cashier 发行记录](https://github.com/laravel/cashier-paddle/releases)、[Pay 的 Paddle Billing 文档](https://github.com/pay-rails/pay/blob/main/docs/paddle_billing/1_overview.md)、[Pay 发行记录](https://github.com/pay-rails/pay/releases)、[Lago 支付支持列表](https://getlago.com/docs/guide/payments/payment-providers)、[Lago 许可证](https://github.com/getlago/lago/blob/main/LICENSE)、[Python SDK 发行记录](https://github.com/PaddleHQ/paddle-python-sdk/releases)、[SDK v1.15.0 许可证](https://github.com/PaddleHQ/paddle-python-sdk/blob/v1.15.0/LICENSE)。

实现时锁定 SDK 及新增传递依赖版本，记录来源、许可证和分发包校验和；适配层验证超时、分页、错误转换和写请求重试行为。未知付款创建不得因更换 SDK 自动重发。此次仅调研，不安装依赖。

## 2. 三个权威来源与 ID 绑定

| 数据 | 权威来源 |
| --- | --- |
| 商品价格、币种、税费、收费周期、试用周期、交易与订阅收款状态 | Paddle |
| 是否上架、用户可买什么、买后发什么、有效期与重复购买规则 | 本系统商品配置 |
| 用户当前可用权益、额度预占/已用、每笔发放及撤销 | 本系统权益账本 |

后台按 **支付连接 + 环境 + `pri_` 价格 ID** 建立映射；`pro_` 产品 ID 用于分组和归属校验。不能只按 `pro_` 发放，因为同产品可能存在月付、年付、一次性和试用价格。

`txn_` 是每次交易的身份，不是重复配置的商品标识。处理完成的交易时，逐一读取账单行的价格 ID，找到已绑定的规则。`txn_`、`txnitm_` 与规则 ID 共同定位一次发放；续费还校验订阅项目与账期唯一性。

价格匹配不能替代用户归属证明。首次购买必须绑定服务器创建的本地订单与交易；续费绑定已验证的本地订阅及客户。不能仅凭邮箱、前端传入用户 ID 或可修改的 custom_data 发放。没有可信归属的外部交易进入待核实记录。

Paddle 产品/价格语义与账单行依据：[Prices](https://developer.paddle.com/api-reference/prices/)、[Get a transaction](https://developer.paddle.com/api-reference/transactions/get-transaction/)。

## 3. 后台怎么配置

增加“商品与权益”和“支付记录”后台页面，沿用现有管理员鉴权。

### 3.1 权益模板

定义有类型、有校验的权益原语；管理员使用表单组合，不能上传脚本或编写 SQL：

| 原语 | 可配置内容 |
| --- | --- |
| 会员访问 | 授予哪个会员模板；有效期跟随账期、试用期或指定天数 |
| 模式使用 | 常规是否不限量、重绘是否需要有效有限页数 |
| 页数额度 | 常规/重绘、数量、是否允许无 PLUS 使用、有效期、发放节奏 |
| 队列权益 | 每模式在途容量、实时名额、同级调度权重；受平台安全上限约束 |

PLUS 是内置的可配置会员模板及展示名称，不再隐含“自动发 300 页”。购买 PLUS 与发放重绘页数是可组合的两项规则。额外购买的重绘页数可以显式允许普通用户使用，但不会自动提高队列容量。

系统免费基线和会员模板统一参与权益计算。布尔权限取有效来源的并集，容量/权重采用明确的最大值合并，页数按有效额度桶合计；两个重叠 PLUS 不翻倍队列容量。PLUS 常规不限量时不消耗常规有限额度。

### 3.2 商品与价格绑定

管理员创建商品，填写名称、说明、排序和可见性，选择订阅或一次性购买。输入或从 Paddle 同步列表选择价格 ID，后端读取并展示真实产品、金额、币种、周期、试用和状态。

一个商品版本包含：

- 展示资料、购买类型、可售时间、限购与会员互斥组。
- 价格绑定：连接、环境、价格 ID、产品 ID、核实时间与价格信息快照。
- 试用规则：资格范围、对应的试用价格、试用权益；无试用购买的价格绑定。
- 正式规则：每个已结清账期发放哪些权益；一次性购买发放哪些权益。
- 有效期、数量处理、重复购买合并、退款处理策略。

同一连接/环境/价格在同一有效区间只能有一个明确的销售映射；试用和无试用价格可以绑定同一商品权益版本。前端不能任意替换价格 ID。

### 3.3 示例，仅说明配置能力

| 商品 | Paddle 映射 | 发放规则示例 |
| --- | --- | --- |
| PLUS 月订阅 | `pri_monthly_example` | 当前付费账期的 PLUS + 300 页重绘，账期末到期 |
| PLUS 试用入口 | `pri_trial_example` | 已核实试用期内 PLUS + 30 页；转付费后使用正式规则 |
| 重绘 100 页包 | `pri_redraw_pack_example` | 一次性 100 页重绘，支付完成起 90 天有效，可不授予 PLUS |
| PLUS 30 天通行证 | `pri_pass_example` | 一次性 PLUS 30 天；是否附带页数单独选择，不创建自动续费 |

数量默认 1；只有商品显式开放数量时，额度按数量乘算。会员时长是否倍增必须单独配置，不能随账单数量隐式推导。一次性时长可配置支付完成即起算或接续同类通行证；默认即时起算，与订阅并行，不改变 Paddle 扣款日期。

### 3.4 发布与版本

草稿可编辑，发布执行完整校验；发布后规则不可原地覆盖。修改生成新版本，旧版本及其映射为履约保留。商品下架只禁止新购买，不取消已有订阅、不停止已经售出的权益发放。

本地订单在结账前固定商品版本及价格快照；订阅项目固定签约版本。默认新版本只作用于新购买，旧订阅续费仍按签约版本履约。改变存量订阅规则必须是独立、明确生效日期的操作，不作为普通“保存商品”副作用；首版不提供自动批量迁移存量订阅。

Paddle 价格若被外部修改，重新核对新订单；旧交易按其实际账单快照及已售版本处理，不拿当前目录价格否认历史付款。

## 4. 用户动态购买

增加商品目录 API，返回当前用户可见商品、权益摘要、试用资格、购买限制、报价和可执行操作。插件的购买卡片、确认页与账户管理均读取该 API，删除硬编码的 9.99、7 天、30 页和 300 页文案。

价格、币种和税费使用 Paddle 价格预览，由后端适配层处理并适当缓存；缺少用户税务地点时明确显示基础价及结账确认金额，不猜税费。插件保留 MV3 CSP，不加载远程 Paddle.js；托管 HTTPS 结账页加载官方 Paddle.js。

用户提交本地商品版本及数量，后端重新校验可售状态和购买资格，再创建订单/交易。网页回调只显示“付款确认中”；账户区分“付款完成”“权益待发放”“权益已生效”，可主动刷新恢复。

商品下架或价格变化时，未创建的购买要求刷新；已创建、已冻结的有效订单按原约定核实履约。存在未知交易结果时恢复同一订单，不能把网络错误变成第二次购买。

依据：[Paddle 价格预览](https://developer.paddle.com/api-reference/pricing-preview/)、[动态价格页](https://developer.paddle.com/build/checkout/build-pricing-page/)。

## 5. 支付到发放的流程

```mermaid
flowchart LR
    A[后台发布商品版本] --> B[用户读取动态目录]
    B --> C[服务端冻结订单与规则]
    C --> D[Paddle 托管结账]
    D --> E[验签回调持久化]
    E --> F[后台查询 Paddle 核实交易与账单行]
    F --> G[解析绑定的商品版本]
    G --> H[原子写入发放回执与会员/额度]
    H --> I[统一权益查询]
    I --> J[翻译预占、结算、释放]
```

Paddle 负责收款、续费、税务和订阅状态；本系统不再实现第二个自动扣款引擎。可靠性由本地持久化事件、对账游标、账户锁和唯一发放约束保证，SDK 不替代这些机制。

### 5.1 试用、续费与一次性购买

- 试用按该价格真实 trial dates 和冻结的试用规则发放；资格由账户及配置的试用组唯一约束，不能因换商品版本重复领取。不是简单通过零金额交易推断试用。
- 正式订阅按核实的已结清账单行及其覆盖期发放；不根据 `active` 或预计下次扣款日期提前发下月额度。
- 一次性额度包不要求 `subscription_id`，独立依赖已完成交易、可信订单绑定和一次性规则。
- 允许正常折扣、余额抵扣；不再用 `grand_total > 0` 判断是否有效结清。零金额交易仍须区分试用、获准折扣与正式账期，不能一律发正式权益。
- 有效期使用上游已核实账期或付款完成时间，不用回调到达时间；迟到消息不会把期限整体后移。
- 同一商品可同时发会员和多种模式额度，整个交易在一个本地事务中核实并发放；未知或冲突账单行使该交易进入待处理，不静默部分履约。
- 常规账期、试用、一次性购买、按比例变更分别分类。首版同一互斥组已有订阅时提供管理/取消，取消并到期后可以购买另一商品；不提供期中按比例升降级或预约换套餐售卖。外部期中变更进入可审计处理，不按一次新月费重复发全额额度。

年付等长账期如配置为逐月发额度，建立已付款覆盖期内的发放计划，按会员锚点逐期开放；不一次性开放全年页数。查询/受理时可幂等补齐当前有效期，后台持久化补查，不依赖某个整点任务。未付款的未来月份不得产生权益。

Paddle 文档将 `completed` 定义为已结清且处理完成；`grand_total` 是抵扣 credit 后、支付前的应付金额；按比例变更可能产生独立交易，不能仅按价格命中就重复履约。依据：[交易完成事件](https://developer.paddle.com/webhooks/transactions/transaction-completed/)、[交易字段](https://developer.paddle.com/api-reference/transactions/get-transaction/)。

### 5.2 取消、暂停、失败与恢复

- 取消续费默认保留已售有效期，取消行为与撤销权益是两件事。
- 扣款失败不发新权益；宽限期首版默认为 0，并作为明确配置项，不通过 `past_due` 自动获得无限常规。
- 暂停停止未来发放；已核实、已购买的当期权益默认保留至原截止时间。恢复不重发已发过的账期。
- 到期不影响已受理翻译按原额度完成，历史授权结果继续按既有保留规则访问。
- 会员互斥组限制重复基础订阅；额度包可以与会员并行，多次购买创建独立桶。
- 维护服务持续核实未终结订单，采用退避与低频长尾补查，删除两天后自动放弃补查的硬截止。无法自动证明结果的订单可进入人工处理，但必须保留唯一订单及处理记录。

### 5.3 发放幂等与对账

事件去重和业务发放去重分开。事件 ID 只去重通知；单次发放用连接/环境、交易行、规则和分期编号唯一识别。试用用订阅项目/试用组识别；周期发放另有订阅项目/覆盖期/规则约束，阻止不同通知或付款替换记录对同一期重复发放。

订单支付状态、权益发放状态、订阅生命周期和异常处理状态分别存储。失败后重跑同一规则版本，不重新读取最新商品规则。交易回执、发放回执、权益记录、额度桶和发放账本在同一数据库事务内提交。

事件处理器与补查使用同一应用服务。使用游标分页、更新时间重叠窗口及持久化扫描进度；进度只有对应页处理成功才推进。乱序订阅快照不能覆盖更新状态；已结清历史账期仍可补入账，不因当前订阅取消而被漏掉。

### 5.4 退款与争议：建议默认策略，待本方案评审

首版必须实现 adjustment 入库、核实、关联原账单行和人工处置页面，不继续只留一个错误码。

- 已批准的整单/整行退款：结束该来源剩余会员访问，关闭该来源额度的新增使用；独立赠送和其他购买保持有效。
- 已消耗量保留审计；已受理翻译按原快照结算。关闭的额度桶即使任务失败释放预占，也不会重新开放使用。不制造负余额，不倒扣其他来源。
- 部分金额退款、单纯税费调整、按比例 credit：不直接按金额比例猜页数，进入后台明确选择“保留权益/回收指定未用额度/结束指定来源访问”的幂等处置；税费变化不能误撤商品权益。
- 正式拒付：默认关闭所涉来源的新使用；预警只标记核实。拒付撤销按原发放记录恢复尚在有效期的剩余权益，不重新发满额、不延长原期限。
- 发放前先核对已知 adjustment，避免退款先到、付款后到导致重新授予；发放后也对账补偿。回收/恢复均为独立审计记录，不删除历史发放。

本项目处置已发生退款对权益的影响，不把本次重构解释为自动向 Paddle 发起退款。依据：[退款与 credit](https://developer.paddle.com/build/transactions/create-transaction-adjustments/)、[Adjustment 列表与行归属](https://developer.paddle.com/api-reference/adjustments/list-adjustments/)。

## 6. 数据与模块边界

以下为概念模型，具体命名在实现中统一；不按旧表字段设计兼容结构。

| 领域 | 数据职责 |
| --- | --- |
| 商品目录 | 商品、不可变商品版本、权益规则、会员模板、Paddle 价格绑定 |
| 支付连接/客户 | 环境与商户连接身份、平台账户和 Paddle 客户的可信映射；密钥留在后端 |
| 订单 | 用户、商品版本、数量、报价/规则快照、原始操作编号、上游交易和未知创建状态 |
| 订阅及项目 | Paddle 状态、项目价格、签约版本、试用与账期、计划取消/暂停/变更 |
| 交易及账单行 | 上游事实、价格 ID、数量、覆盖期、结清状态和处理版本 |
| 权益发放 | 原交易行/试用/运营来源、规则版本、有效期、会员访问与额度发放计划 |
| 额度与用量账本 | 独立额度桶、预占/已用、关闭状态、撤销/恢复流水及任务关联 |
| 事件与对账 | 验签事件收件箱、租约/重试、扫描游标、adjustment、人工处置和管理员审计 |

会员来源改为多条授权记录，不再把运营会员和支付会员分别塞到 `User.plus_*` 与 `User.billing_plus_*` 两组字段中。管理员赠送走同一权益服务，并保留来源、备注和幂等编号。

翻译调度消费一个可重建的当前权益投影，投影携带版本和下一生效/到期边界；变更同事务刷新，到边界按需重新计算。不得因缓存 PLUS 标记未刷新而继续放行，也不在每次任务检查时访问 Paddle。

额度保留“最早到期先使用、受理绑定原桶、成功结算、失败释放、无限权益独立记录”的业务语义；删除用 `source_key.startswith('paddle:')` 判断业务的代码，改用类型化来源及明确外键。是否可用同时检查权益时间与桶状态。

建议模块拆分：`catalog`（商品配置）、`commerce`（订单/订阅与履约）、`payments/paddle`（SDK 适配与上游标准化）、`entitlements`（访问/额度/投影）。只有适配层理解 Paddle 报文字段，商品规则解释器只消费经过验证的业务事实。

## 7. 新接口与界面范围

- 管理员：商品草稿编辑/发布/下架、权益模板、Paddle 价格同步与校验、订单/订阅/发放流水、重试核实、退款权益处置。
- 用户：动态商品目录与报价、创建/恢复订单、订单状态、订阅列表及取消/门户、现有权益与额度来源。
- 系统：Paddle Webhook、独立持久化对账维护、权益分期计划恢复。

具体接口在实施时由新的 OpenAPI 定义，删除旧单套餐接口契约与前端调用，不提供兼容别名。重用 `/v1/me/entitlements` 等稳定业务概念可以保留路径，但必须同步客户端类型和相关检查，不保留双版本逻辑。

购买页面从规则生成主要权益摘要，避免实际发 100 页但卡片写 300 页；自由文案只用于补充说明。后台发布时展示试用、首购、续费、到期与退款后的效果预览。

## 8. 旧实现删除与数据库切换

本轮实施按用户要求不做旧支付数据迁移、字段兜底、双写、兼容路由或旧模型适配。

删除/替换范围：

- 现有 `billing_checkout.py`、`billing_sync.py`、`billing_models.py`、`billing_api.py` 的单套餐实现；替换原手写 `paddle_client.py` 的协议实现。可保留独立仍有价值的算法和测试意图，但只接到新模型上。
- `PADDLE_PRODUCT_ID`、`PADDLE_TRIAL_PRICE_ID`、`PADDLE_STANDARD_PRICE_ID` 和校验中的固定金额/周期/页数；连接凭据与环境配置仍保留。
- `User` 上两套会员事实字段、Paddle 字符串前缀判断、运营赠送与订阅分开的有效期拼接逻辑；改为统一授权来源和可重建投影。
- 客户端固定单套餐购买 UI、旧 API 类型和只有单订阅的返回结构；替换为目录和订阅项目视图。
- 旧支付迁移结构、旧支付测试夹具、旧沙盒初始化及依赖旧表的验证脚本，更新为新结构；同步会员/架构/运行文档和过时产品限制。

已有额度结算算法、任务快照、缓存复用、权限隔离和供应商成本计量仍有用途，按新来源模型改造并继续验证，不为“删旧代码”重写无关翻译算法。

开发与验收使用全新隔离数据库。新版本只接受新结构，旧库直接报错，不自动 stamp 成新版本。实际切换使用明确的新数据库/新 schema，不读取或回填旧支付数据；旧数据库退役删除在确定目标后执行。此方案不授权本轮清空用户图片、R2 对象、现有运行数据库或取消 Paddle 上游订阅。删除本地表也不会取消 Paddle 扣款，因此实际部署前要盘点并明确处理尚存的上游订阅，不能遗留持续扣款但无法履约的对象。

## 9. 实施与完成标准

按一个完整重构交付，步骤用于组织实现，不把只建表或只接回调当作完成：

1. 建立新商品、规则、授权和支付模型，接入固定版本官方 SDK；形成新库初始化入口。
2. 完成管理后台配置/发布、用户动态目录与报价、订单/托管结账。
3. 完成试用、一次性购买、续费、取消/暂停、未知创建恢复、持续对账及退款处置。
4. 统一管理员赠送、会员投影和翻译受理/结算，删除旧实现与过时文档约束。
5. 完成隔离自动化、PostgreSQL 并发、浏览器和真实 Paddle 沙盒验证，分别报告证据。

必测场景：

- 不改代码，仅后台绑定两个不同价格即可分别售卖 PLUS 组合和纯页数包；下架后停止新售、存量续费继续履约。
- 两种价格/环境隔离；错误归属、非配置价格、改数量和伪造用户拒绝；试用防重复。
- 一次性订单无订阅 ID 也能发放；同单多权益全成或全败；相同价格不同规则版本按订单/签约快照履约。
- 重复/乱序事件、丢回调、进程崩溃、未知创建、超过两天补查、分页中断、不同事件指向同账期不重复发。
- 正常付款、余额全额抵扣、折扣结清、试用零金额、未付款、按比例变更不能混淆。
- 跨期任务、到期降级、赠送叠加、最后一页并发预占、退款关闭后释放不复活、退款先于付款消息和拒付撤销。
- 前端 Chrome/Edge 检查动态商品、试用说明、金额、购买中/未知/失败/发放中状态、取消及到期提示；不破坏阅读位置。
- 新库从零建表，无旧表/旧字段运行依赖；必要契约、构建和 PostgreSQL 检查通过。未实际运行的外部验收不得记为通过。

## 10. 本方案的明确取舍

- 采用官方 Python SDK，但权益配置后台由本项目实现；不引入第二套 PHP/Ruby 运行服务。
- 首版支持配置化订阅、一次性页数包和限时会员，以及可选试用；不自动发布新的商业套餐。
- 已售规则按版本冻结；新配置不追溯改旧订单与订阅。
- 首版不做期中按比例自助升降级或预约换套餐；支持取消与到期后的新购。以后若增加切换，需要独立的变更计划与履约版本，不能通过修改目录映射实现。
- 退款/争议采用第 5.4 节提出的默认处置作为评审内容；部分金额变动保留完整人工处置闭环，不用未经确认的金额到页数换算。
- 本次交付到方案，后续实施不保留旧支付兼容层。
