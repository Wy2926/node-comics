# RX 6900 XT v1 方案负载测试

本文保留 v1 基线及最初定位过程。后续已完成 [多进程吞吐测试](AMD_PARALLEL_TEST.md)，并将 [单页优化](AMD_SINGLE_PAGE.md) 接入默认 AMD v2；请勿将下方 v1 数字视为当前默认版本的性能。

## 2026-09-15 实测结论

本机 RX 6900 XT 16 GiB、Ryzen 7 5800X（16 逻辑核）、32 GB RAM；AMD 驱动 `32.0.21030.2001`，固定 PyTorch 2.4.1 / DirectML 0.2.5.dev240914、CPU 线程数 4。当前实现对该样本的本地处理能力约 **11 页/分钟**，GPU 仍有大量空闲。

正式轮为 `private-test-data/amd-load-20260915-232520/`，计时阶段合计 495.236 秒、92/92 页成功；另外 1 页完整预热成功。全部 93 页的最终像素哈希相同，抹字及字形掩膜相同，无缓存重建、OCR 漂移或受保护像素改动。

| 请求并发 | 页数 | 吞吐（页/分钟） | 平均单页延迟 | P95 单页延迟 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 6 | 10.64 | 5.64 秒 | 5.70 秒 |
| 2 | 6 | 11.21 | 10.60 秒 | 10.95 秒 |
| 4 | 8 | 11.28 | 20.83 秒 | 21.50 秒 |
| 8 | 16 | 11.39 | 40.97 秒 | 42.09 秒 |
| 持续单路 302.42 秒 | 56 | 11.11 | 5.40 秒 | 5.57 秒 |

从双路增加到八路，吞吐仅增加约 1.6%，平均延迟增加到约 3.9 倍。当前单执行位下，继续堆请求主要增加排队。

| 引擎进程资源 | 测量值 |
| --- | --- |
| GPU 最忙引擎利用率 | 各阶段均值 2.46%–7.10%；持续阶段均值 5.75%，全程采样峰值 23% |
| GPU 独占显存 | 峰值 3.08 GiB；持续阶段保持该水平 |
| GPU 共享内存 | 峰值 0.32 GiB |
| CPU | 各阶段平均约 2.94–3.16 个逻辑核，相当于整机逻辑 CPU 约 18%–20% |
| 常驻物理内存工作集 | 峰值 2.14 GiB |
| 私有提交内存 | 峰值 5.39 GiB；持续阶段由 5.20 增至 5.33 GiB |
| 图像缓存 | 从持续阶段开始前 94.79 MiB 增至 238.26 MiB，未达到 256 MiB 上限 |

持续阶段前 10 页平均 5.52 秒、后 10 页 5.36 秒，没有观察到逐渐变慢、OOM 或进程崩溃。内存增长与缓存累积同时发生，本轮没有覆盖缓存达到上限后的长时间运行，因此不宣称已经排除长期泄漏。

持续阶段内部平均检测/OCR 3.06 秒、LaMa 1.22 秒、嵌字 0.41 秒；其余约 0.71 秒为 HTTP、编解码、数据传递和客户端验证。结合低 GPU 利用率、固定单执行位和保留在 CPU 的模型模块，证据指向当前串行混合流水线限制吞吐。尚未做逐算子 CPU/传输时间归因，不能将此结果称为 6900 XT 的硬件计算上限。模型权重与质量标准没有改变。

原始证据包括 `report.json`、`pages.jsonl`、`resources.jsonl`、`profiles/execution-summary.json` 和 `first-result.png`。可入库的无图片文字摘要见 [实测数据](evidence/amd-load-20260915.json)。测试后引擎和监控进程已关闭。

## 2026-09-16 补充分段定位

同一张样本完整预热后测量 3 次，保持原模型、CPU 线程数及全部图像处理；3 次输出均与预热像素完全一致。以下是模块边界墙钟时间，包含实际同步等待；不是 GPU kernel 计时。

| 模块 | 每页平均耗时 | 说明 |
| --- | ---: | --- |
| 检测 | 0.126 秒 | GPU 网络与检测包装过程 |
| OCR 总计 | 1.976 秒 | 其中视觉骨干/编码及传递 0.077 秒，CPU 解码器 1.278 秒；剩余为束搜索控制、预后处理等 |
| 分镜识别与阅读顺序排序 | 0.890 秒 | `sort_regions` 的 CPU 路径，不只是文本框坐标排序 |
| 文本区域合并 / 掩膜细化 | 0.054 / 0.239 秒 | CPU |
| LaMa 修复阶段 | 1.334 秒 | 10 个局部裁剪依次处理；共调用 FourierUnit 360 次 |
| FourierUnit CPU 数学运算 | 0.568 秒 | LaMa 的子项；计入边界传递和等待后为 0.718 秒 |
| 嵌字阶段 | 0.474 秒 | 包含该阶段图像编码 |

整体函数调用与结果解码平均 5.186 秒，不含 HTTP。PNG 编码合计 0.324 秒、解码 0.089 秒，已包含在上述父级阶段或整体时间中，不可重复相加。无图片内容的采样数据见 [模块计时](evidence/amd-components-20260916.json)。

当前有三层串行约束：compute-agent 注册容量固定为 1 且逐项领取；引擎对整个阶段持有设备锁；单服务事件循环直接执行同步模型和 CPU 图像处理。相同物理 `resource_id` 还会被控制端拒绝重复注册。因此增加请求、复制同配置容器或单改 capacity 都不等于获得模型并行。

随后已验证同一物理 GPU 内 1/2/4 个独立模型进程，并保持原模型和像素质量校验，结果见 [多进程吞吐测试](AMD_PARALLEL_TEST.md)。正式 agent 多执行位仍需要并行领取、引擎进程调度及有界设备准入；用户后续以单页延迟为目标，当前默认入口采用单 GPU 实例及页内 CPU 分镜进程。

### 原 OCR 网络全 GPU 的隔离实验

2026-09-16，进一步将解码器移到 GPU。直接迁移仍得到 7 个文本块而非原来的 11 个；保留 CPU 束搜索、仅迁移解码器数学运算也出现相同退化，排除了仅由 GPU 束搜索控制引起的解释。

对相同的 CPU 参考输入逐步比较：前 3 步 GPU 解码输出最大绝对误差约 `1e-6` 至 `2e-6`，但历史状态缓存误差高达 6.84–8.95。将 `cached_activations[:, layer, step, :] = value` 的原地切片更新改为等价的逐层拼接、stack 重建，并处理 step=0 的空前缀后，缓存误差降到约 `1e-6` 至 `2e-6`。此结果将主要偏差定位到本机 DirectML 缓存切片写入路径。

应用该修正后，原 OCR 神经网络、解码和预测头全部迁到 GPU；将最终张量统一复制回 CPU 做文字/颜色后处理，避免逐字符 `.item()` 的大量小传输。完整预热后各计时 3 次：

| 检测/OCR 阶段（含排序、掩膜） | 3 次耗时 | 平均 |
| --- | --- | ---: |
| 现用 GPU 编码 + CPU 解码 | 3.500 / 3.297 / 3.437 秒 | 3.411 秒 |
| 实验 GPU 编码 + GPU 解码 | 3.172 / 3.063 / 3.125 秒 | 3.120 秒 |

阶段耗时减少约 8.5%。3 次文本和掩膜均与原方案一致；最终嵌字对照的字形掩膜和译图像素完全一致。无图片文字的证据见 [GPU OCR 实验](evidence/amd-gpu-ocr-probe-20260916.json)。

这是最初的隔离实验；后续 GPU OCR 修正经过多进程持续负载，并随单页优化接入 AMD v2。v2 完成 30 张单页 HTTP 对照，尚未完成多语言质量集。自回归逐步依赖、Python 控制及其他 CPU 处理仍然存在；“OCR 网络能上 GPU”不能等同于“整个流程能够吃满 GPU”。

## 范围与复现

本机 Windows 原生 DirectML 引擎，原检测器、48px OCR、LaMa Large 和原嵌字器；运行配置见 [原模型部署与质量验收](AMD_GPU_VALIDATION.md)。本次只新增测试工具，不调整执行位、模型、CPU 线程数或生产调度。

在仓库根目录执行：

```powershell
services/classic-engine/.venv/Scripts/python.exe scripts/benchmark_amd.py --baseline-v1 --soak-seconds 300
```

前提是本机模型与依赖已准备，且 `private-test-data/amd-original-models/stages.json` 保存了原样本一次成功翻译的分段和译文。可通过既有 `scripts/start-local-amd.ps1 -Smoke` 建立该文件；首次真实翻译会调用配置的在线服务，后续负载测试本身不调用文本服务或 R2。

测试独立启动回环地址 `127.0.0.1:18090` 的引擎，端口占用即失败，结束后关闭自己启动的进程。输出默认位于独立的 `private-test-data/amd-load-时间戳/`，重复运行不覆盖先前记录。监控 PowerShell 采用仅对本次子进程生效的执行策略，不修改系统策略；跟踪虚拟环境启动器的实际 Python 子进程。

### 工作负载

- 一张项目原创英文漫画，1024×1536、11 个文本块，译为简体中文。
- 每次都通过真实 HTTP 顺序执行 `analyze → inpaint → render`；检测、OCR 和 LaMa 每页重新运行。
- 每页使用独立 scope，避免跨页复用修复缓存而虚增吞吐；同页 render 正常复用刚生成的修复结果。
- 复用同一份已验证译文，隔离供应商延迟、费用及文本生成随机性。
- 预热一整页，然后依次施加 1/2/4/8 路闭环请求，页数分别为 6/6/8/16；最后以当前单执行位连续运行至少 300 秒，排空已开始的页面。
- 每页检查 OCR 分段、尺寸、源图哈希、抹字与字形掩膜、受保护像素；统计相对预热译图的逐像素差异和输出哈希。

### 指标定义

- **吞吐**：该阶段成功页数除以实际墙钟时间，包含本地 HTTP、PNG/JSON 编解码和客户端图片验证。
- **单页延迟**：该页三个 HTTP 阶段及验证的总耗时；多路包含引擎排队时间。阶段内部计时不包含队列等待。
- **并发**：等待引擎处理的客户端页数；模型执行位始终为 1。此项不代表多个模型副本并行，也不验证控制端会员公平队列。
- **GPU 利用率**：Windows `GPU Engine` 性能计数器中该引擎进程最忙引擎的采样利用率；不叠加不同 GPU 引擎，不混入桌面程序。采样间隔约 1.4 秒，不能反映更短的瞬时尖峰。
- **显存**：该引擎进程的 DedicatedUsage；共享 GPU 内存单列。与全桌面显存占用不同。
- **CPU**：进程 CPU 时间增量 / 墙钟时间，100% 表示一个逻辑核；5800X 有 16 个逻辑核。
- **内存**：工作集和私有提交量分别记录。私有提交量包括运行时保留内存，不等于常驻物理内存；图像缓存上限是 256 MiB。

所有图片、OCR、译文和原始运行记录均保留在 Git 忽略目录。测试不创建 Docker 容器，不访问任务数据库。

## 验收边界

这是当前实现对一张代表性页面的短时持续吞吐测试。不能据此承诺所有分辨率、文本密度、多语言、全天候稳定性，或包含在线 LLM/R2 的产品端到端容量；也不将“请求不断”解释成“GPU 硬件利用率 100%”。

本次前两轮因资源监控启动与 Windows 虚拟环境进程归属问题中止，只作为仪器调试；人为停止引擎造成的请求失败不计入正式负载结果。正式轮在预热后校验实际 GPU 进程资源采样，再开始统计。
